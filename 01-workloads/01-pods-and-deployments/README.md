# Lab 1: Pods and Deployments

## Objective

Create and inspect an NGINX Pod using imperative and declarative methods, then verify that the application is accessible through the Pod network.

## Concepts covered

- Kubernetes Pods
- Imperative resource creation
- Declarative YAML manifests
- Pod lifecycle and status
- Labels
- Container ports
- Pod networking
- JSONPath queries
- Resource deletion

## Environment verification

The Kubernetes cluster was checked before creating any workloads:

```bash
kubectl cluster-info
kubectl get nodes
```

Output:

```text
NAME           STATUS   ROLES           AGE   VERSION
controlplane   Ready    control-plane   18d   v1.36.1
```

The `Ready` status confirmed that the node was available to run workloads.

## Creating a Pod imperatively

The first Pod was created directly from the command line:

```bash
kubectl run my-first-pod --image=nginx:1.21
```

Output:

```text
pod/my-first-pod created
```

The Pod initially entered the `ContainerCreating` state:

```text
NAME           READY   STATUS              RESTARTS   AGE
my-first-pod   0/1     ContainerCreating   0          11s
```

After the NGINX image was downloaded and the container started, the Pod entered the `Running` state:

```text
NAME           READY   STATUS    RESTARTS   AGE
my-first-pod   1/1     Running   0          47s
```

This was an imperative approach because the resource was created directly using command-line arguments.

## Creating a Pod declaratively

A second Pod was defined using a Kubernetes YAML manifest:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-declarative
  labels:
    app: nginx
    environment: lab
spec:
  containers:
    - name: nginx
      image: nginx:1.21
      ports:
        - containerPort: 80
```

The manifest was applied to the cluster:

```bash
kubectl apply -f nginx-pod.yaml
```

Output:

```text
pod/nginx-declarative created
```

This was a declarative approach because the desired state was stored in a YAML manifest that can be version-controlled and applied repeatedly.

## Verifying the Pods

The Pods were inspected using:

```bash
kubectl get pods
kubectl get pods -o wide
```

Output:

```text
NAME                READY   STATUS    RESTARTS   IP              NODE
my-first-pod        1/1     Running   0          192.168.0.193   controlplane
nginx-declarative   1/1     Running   0          192.168.0.148   controlplane
```

The output confirmed that:

- Both Pods were running.
- Each Pod contained one ready container.
- Each Pod received its own internal IP address.
- Both Pods were scheduled onto the `controlplane` node.

## Inspecting the declarative Pod

The complete configuration and runtime state were inspected:

```bash
kubectl get pod nginx-declarative -o yaml
```

The output included:

- The original metadata and labels
- The NGINX container image
- The exposed container port
- The Pod IP address
- The assigned node
- The container state and restart count
- Pod readiness and scheduling conditions
- Additional configuration generated by Kubernetes

## Testing the application

The Pod IP was retrieved using JSONPath:

```bash
POD_IP=$(kubectl get pod nginx-declarative \
  -o jsonpath='{.status.podIP}')

echo "Pod IP: $POD_IP"
```

Output:

```text
Pod IP: 192.168.0.148
```

An HTTP request was then sent directly to the Pod:

```bash
curl "$POD_IP"
```

The request returned the NGINX welcome page:

```html
<h1>Welcome to nginx!</h1>
```

This confirmed that the NGINX application was responding over the Kubernetes Pod network.

A `Running` Pod does not automatically prove that its application is working. Testing the application provided stronger verification.

## Troubleshooting

The original imperative command used a single hyphen:

```bash
kubectl run my-first-pod -image=nginx:1.21
```

This returned:

```text
error: unknown shorthand flag: 'm' in -mage=nginx:1.21
```

The `image` option is a long-form flag and requires two hyphens:

```bash
kubectl run my-first-pod --image=nginx:1.21
```

## Cleanup

The imperatively created Pod was deleted:

```bash
kubectl delete pod my-first-pod
```

Output:

```text
pod "my-first-pod" deleted from default namespace
```

The remaining Pod was verified:

```bash
kubectl get pods
```

Output:

```text
NAME                READY   STATUS    RESTARTS   AGE
nginx-declarative   1/1     Running   0          2m1s
```

The Pod phase was extracted using JSONPath:

```bash
kubectl get pod nginx-declarative \
  -o jsonpath='{.status.phase}{"\n"}'
```

Output:

```text
Running
```

To remove the declaratively created Pod:

```bash
kubectl delete -f nginx-pod.yaml
```

## What I learned

- A Pod is the smallest deployable unit in Kubernetes.
- Pods can be created imperatively using commands or declaratively using YAML manifests.
- Declarative manifests provide a repeatable approach that can be stored in version control.
- Kubernetes assigns each Pod an internal cluster IP address.
- A `Running` status does not by itself prove that the application is responding.
- JSONPath can extract specific information from Kubernetes resources.
- Standalone Pods do not provide the self-healing and scaling capabilities offered by Deployments.
